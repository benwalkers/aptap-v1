# Engineering Notes — ApTap Release 2

## Data defects and decisions

July/August source files use signed CSV values and ISO booking dates; September/October JSONL uses GBP magnitude plus `direction`, with `posted` day-first and optional explicit ISO date, leading `£`/`GBP` and thousands grouping. Additive JSON keys are ignored safely. Invalid dates, amounts, customer IDs or currency go to `rejected_rows.csv`. The August file contains 1,052 July-dated rows (valid back-posting, not automatically an error). A bank-scoped `transaction_id` remains stable through migration; duplicate occurrences have been observed. Two human merchant labels are demonstrably wrong: `TESCO MOBILE` is mobile and `OCTOPUS ENERGY` is energy; corrected in separate curated aliases, not by altering the raw label file.

**Correction policy:** latest *valid observed delivery* wins, using stable filename/row order on first load and committed delivery order thereafter. An identical canonical payload is rejected as duplicate; an actual resend correction supersedes the former active row and audits it with its original raw payload and a `transaction_corrections` lineage record. Invalid resends cannot supersede. Since the bank gives **no source version/update time**, the last received record is not guaranteed objectively authoritative; production should obtain source sequence metadata. Every ingested occurrence remains either active Silver or rejected/superseded, and `raw=clean+rejected` is enforced. Bronze raw bytes and per-file checksums are retained locally.

## Classification and features: what is not verified

The employer's scored output permits **only ten categories**. The CLI always returns one of those ten plus `needs_review`; unfamiliar descriptors have a provisional top-1 lexical category, not approved classification. Internally `REVIEW_REQUIRED` is a workflow status rather than an eleventh category. Unreviewed predictions never feed bill or switch calculations. The existing curated aliases are **synthetic demo assumptions** and require bank-approved product verification; multi-service insurance/telecom names can be ambiguous. Only 57 descriptions are labelled with imbalanced class support; leave-one-description-out lexical and optional MiniLM metrics are exploratory, not independent holdout scores or calibration. Merchant-level model drift and reviewed precision are unmeasured.

Bills require observations in the reporting month and may be `monthly_candidate` if history is insufficient. Switches are **candidate** sequential provider-payment patterns, not proof of cancellations. A read-only independent Silver validation checks supporting IDs, timeline, trusted aliases, full provider payment history, median differences and absence of concurrent providers; extra evidence is in `switch_evidence.csv` and `switch_validation_summary.json` without changing scored `switches.csv`. Evidence tiers are provisional, repeated new-provider months and supported two-sided payment pattern, **never externally confirmed**. Observed median bill changes do not establish causal savings, especially given July–September's short horizon; there may be confounding, selection and price-plan effects. A one-page chart/report presents uncertainty, not promised savings. October automatically sets the as-of date to `2026-10-31` based on the **source period**; `--as-of` overrides.

## Scale, privacy, monitoring and costs

This is a **measured local Python/SQLite prototype**, not a tested distributed pipeline. At 1,500 synthetic customers, September has 44,950 source records; extrapolating to 15M customers suggests **~449.5M transactions per month** and ~64.6 GB of raw JSONL (assumes identical rates/bytes per customer, unrealistic until profiled). Measure current runtime/memory from `outputs/run_metrics.json`; multiplying by ~10,000 customer-scale factor ignores throughput, I/O and contention and is **not a capacity plan**. SQLite's single-writer model and rerunning downstream customer windows are bottlenecks. Production design: S3 or approved in-bank object landing with chunked resumable uploads + checksum manifests, bank/month-partitioned Bronze, transactional Iceberg Silver `MERGE` on bank+transaction ID, compact partitions, customer/month Gold, and controlled CDC ordering; orchestration with checkpointed backfills. Spark/Iceberg configs are examples, **not runtime verified**.

AWS: encryption, tightly scoped S3/Glue/EMR/IAM and observability. Bank-contained: no personal-data or model-query egress, approved signed dependencies/models, change board, no arbitrary installations, local chunk assembly and manifest validation. Customer IDs and free-text payee narratives are potentially identifying; minimise, tokenise only where suitable, encrypt, apply retention and least-privilege/audit. Only contractually permitted aggregated outputs may leave a bank. Monitor schema/delivery drift, raw/active/reject reconciliation, corrections, review rate and backlog, accepted-label precision via sampled validation, false-switch cases, and category mix drift. Per-million cost: capture measured compute/storage/requests per batch and divide by actual transaction count; **do not extrapolate a verified cloud price from laptop timings**. First week: secure data contract and correction sequencing, establish a merchant-product review policy, run synthetic replay/backfill, and benchmark representative distributed slices inside the deployment boundary.
